
## Архітектура розгортання в Kubernetes

### 1. Призначення сервісу

Для моделювання обрано веб-сервіс **AutoService_web**, призначений для автоматизації обліку заявок та послуг станції технічного обслуговування. Клієнти сервісу використовують його для перегляду доступного каталогу робіт і створення замовлень на ремонт, а адміністратори СТО — для керування переліком послуг та контролю статусів виконання.

### 3. Опис дизайну та шлях запиту

Сервіс **AutoService_web** розгорнуто в Kubernetes-кластері (поверх робочих вузлів `Worker Nodes`) в ізольованому середовищі — namespace **`autoservice-prod`**. Зовнішній трафік від клієнта надходить за доменом **`api.autoservice-app.com`** через DNS на зовнішній `Load Balancer`, який передає запити на **`Ingress`**, де за правилами `Host` та `Path` (`/api`, `/orders`, `/services`) вони маршрутизуються на внутрішній **`Service` (`autoservice-svc`, тип `ClusterIP`)**. Далі `Service` рівномірно балансує запити між **2 Pod-ами**, які керуються через **`Deployment`** (`autoservice-deployment`) — кількість реплік `2` обрано для базової відмовостійкості та можливості оновлення застосунку без простою (Zero-Downtime Deployment). Автоматизація доставки коду реалізована через ланцюжок **GitHub (`github.com/user/AutoService_web`) - GitHub Actions (CI/CD) - GitHub Container Registry (`ghcr.io/user/autoservice-web:1.0.0`)**, звідки вузли кластера завантажують готовий Docker-образ під час запуску Pod-ів.
